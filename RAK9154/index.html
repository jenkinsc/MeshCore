    RAK9154 Solar Battery telemetry (RAK4631 repeater)

    Reads battery voltage from a RAK9154 Solar Battery Output 1 (RAK SensorHub one-wire, 9600 8N1, half duplex – not Modbus) and feeds it to MeshCore's existing battery telemetry, which otherwise reads 0.0 V on this hardware.

    Everything is behind -D RAK9154_BATTERY. The stock RAK_4631_repeater target is unchanged.

    Targets

    env description
    RAK_4631_repeater stock, untouched
    RAK_4631_repeater_RAK9154 stock + -D RAK9154_BATTERY, GPS disabled (-UENV_INCLUDE_GPS), advert name "RAK9154 Repeater"

    Build: pio run -e RAK_4631_repeater_RAK9154 (or bash build.sh; note build.sh needs bash, not dash).

    Architecture

    RAK4631Board::loop() -> RAK9154Battery::loop()   drain RX, validate frames, update cache, send ONE request per poll
RAK4631Board::getBattMilliVolts() -> cache       O(1), never touches the wire; falls back to the stock ADC path if
                                                 there is no fresh RAK9154 reading
    • rak9154/RAK9154Protocol.* – pure framing / checksum / decode (host-testable, no hardware).
    • rak9154/RAK9154Battery.* – cache, state machine (provision -> poll), timeouts, stats, CLI text.
    • rak9154/RAK9154HalfSerial.* – bit-banged half-duplex UART on one pin (GPIOTE falling-edge RX, DWT-timed TX).
    • Poll every 30 s (clamped 15–60 s); cache is stale after 5 min; 1.5 s response timeout; re-provision after 3 timeouts.
    • Blocking: only transmitting a request (~14 ms/poll). RX is interrupt-fed (~1 ms of ISR time per received byte).

    Flags

    flag default meaning
    RAK9154_BATTERY off enable feature
    RAK9154_ONEWIRE_PIN PIN_SERIAL1_RX UNVERIFIED – see below
    RAK9154_DEBUG off serial log lines
    RAK9154_POLL_INTERVAL_MS 30000
    RAK9154_STALE_MS 300000
    RAK9154_RESPONSE_TIMEOUT_MS / RAK9154_REPROVISION_AFTER 1500 / 3 the custom env uses 4000 / 10 during bring-up
    RAK9154_RSP_BIG_ENDIAN / RAK9154_REPORT_BIG_ENDIAN 0 / 1 UNVERIFIED 16-bit byte order
    RAK9154_TX_GAP_BITS 4 idle bit times after every transmitted byte (RAK's reference class spaces bytes ~12 bit times; change live with rak9154 gap <n>, 0-16, not persisted)
    RAK9154_RX_LATENCY_CYCLES 320 ISR entry latency used to centre sampling; tune with a scope

    CLI

    rak9154 (same as rak9154 status), rak9154 diag, rak9154 extra, rak9154 gap [n], rak9154 poll, rak9154 info, rak9154 raw [offset] (pages through the last received frame; replies are limited to ~150 characters, so use e.g. raw 35 and raw 70 for the rest). status shows validity, voltage, age and the diagnostic counters (requests, ok, timeouts, bad checksum, invalid, framing, unknown channels, range rejects).

    Pin verification (REQUIRED before connecting anything)

    The GPIO carrying Output 1 on a WisMesh repeater harness was not established from documentation. The default (P0.15) is what RAK's library and a Meshtastic RAK variant use, nothing more. Before powering: 1. Trace the RAK9154 Output 1 wire to the WisBlock slot pin with a multimeter/continuity (unpowered). 2. Find that pin's nRF52840 GPIO in the RAK4631 schematic; confirm it is not used by the radio, I2C, GPS, or LEDs. 3. Check the probe's logic level is 3.3 V before it touches an nRF52 pin. 4. Set -D RAK9154_ONEWIRE_PIN=<arduino pin> accordingly. Note the GPS option uses some of the same header pins, which is why the custom target disables GPS. 5. First power-up: scope/logic analyser on the line if possible; confirm 9600 baud idle-high frames.

    Channels decoded

    Per RAK's RAK9154 payload decoder (that page documents the LoRaWAN uplink of a RAK2560 hub, which shares the sensor IDs; the one-wire byte order is separate and still unverified here):

    IPSO field size / scale
    0xBA battery voltage 2 B unsigned, 0.01 V
    0xB9 battery current 2 B signed, 0.01 A (+/-1.5 A range)
    0xB8 state of charge 1 B, %
    0x67 temperature 2 B signed, 0.1 C (-30..105)
    0xF3 battery errors and battery FW version 2 B; faults are bits 6..11: 6 over-voltage, 7 charge over-current, 8 charge low-temp, 9 charge high-temp, 10 charge short-circuit, 11 charge over-current lock

    The two 0xF3 entries are told apart only by their channel byte, and RAK documents the channel only for the FW version (example 0x1A). Observed on a real probe: 0x19 = faults (0000, none) and 0x1A = firmware (0004 = V00.04). The driver stores both raw with their channels; rak9154 extra shows them, labelling a word with any bit outside 6..11 as a firmware version and 0 as "no faults". That labelling is a heuristic until it is seen on a real probe. Not published over the mesh yet.

    What appears in the app's telemetry

    channel value source
    1 battery voltage MeshCore's own getBattMilliVolts(), i.e. the cached RAK9154 value (percent in the app is the app's own estimate from the voltage)
    1 state of charge RAK9154 0xB8, LPP percentage
    1 charge current RAK9154 0xB9, LPP current
    1 nRF52 chip temperature MeshCore default, unrelated to the battery
    next free channel (2 with no other sensors) battery temperature RAK9154 0x67
    same channel as the battery temperature fault byte (LPP digital input, 0 = none; bit0 OV, 1 charge-OC, 2 charge-low-temp, 3 charge-high-temp, 4 charge-short, 5 charge-OC-lock) RAK9154 0xF3 fault word (bits 6..11 shifted down)

    Notes: LPP "current" is unsigned, so only charging current is shown and discharge reads 0 A; the probe's sign convention is unverified (compare rak9154 status current by day and night). Battery temperature is not put on channel 1 because the chip temperature is already there and two temperatures on one channel collide in the app. Only requesters with base telemetry permission get the extras (guests see voltage only). The fault word (0xF3) is published as the fault byte; the firmware-version word stays console-only (rak9154 extra). The hook is a few lines in EnvironmentSensorManager::querySensors, guarded by RAK9154_BATTERY.

    Byte-order bench procedure

    Voltage endianness is unverified. With a battery of known voltage: run rak9154 raw and rak9154 info, compare the decoded value. A range rejects count rising means the byte order is wrong; flip RAK9154_RSP_BIG_ENDIAN / RAK9154_REPORT_BIG_ENDIAN and re-test. Please contribute real captures to test/test_rak9154/fixtures.h.

    Tests

    Host tests (53 protocol/driver tests + 15 simulated-hardware tests of the real transport source), ASan/UBSan: see .github/workflows/build-rak9154.yml for exact commands. The existing fixtures are synthetic, built from an independent encoder; they prove internal consistency, not agreement with a real probe.

    What has and has not been verified

    Verified in the development sandbox: host tests; cross-compile of all new/changed sources for Cortex-M4 against the real Adafruit nRF52 headers; with the flag off the board code disassembles identically to upstream and the new sources compile to empty objects; the new env equals the stock env plus four flags.

    Not verified (CI/bench needed): full PlatformIO build of both targets (registry unreachable in the sandbox), booting, any communication with a real RAK9154, the pin, byte order, whether the probe needs provisioning, RX timing margin under radio/USB interrupt load, and any temperature/status field meaning.
