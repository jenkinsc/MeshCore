# RAK9154 Solar Battery telemetry (RAK4631 repeater)

Reads battery voltage from a RAK9154 Solar Battery **Output 1** (RAK SensorHub one-wire, 9600 8N1, half duplex –
not Modbus) and feeds it to MeshCore's existing battery telemetry, which otherwise reads 0.0 V on this hardware.

Everything is behind `-D RAK9154_BATTERY`. The stock `RAK_4631_repeater` target is unchanged.

## Targets

| env | description |
|---|---|
| `RAK_4631_repeater` | stock, untouched |
| `RAK_4631_repeater_RAK9154` | stock + `-D RAK9154_BATTERY`, GPS disabled (`-UENV_INCLUDE_GPS`), advert name "RAK9154 Repeater" |

Build: `pio run -e RAK_4631_repeater_RAK9154` (or `bash build.sh`; note `build.sh` needs bash, not dash).

## Architecture

```
RAK4631Board::loop() -> RAK9154Battery::loop()   drain RX, validate frames, update cache, send ONE request per poll
RAK4631Board::getBattMilliVolts() -> cache       O(1), never touches the wire; falls back to the stock ADC path if
                                                 there is no fresh RAK9154 reading
```
- `rak9154/RAK9154Protocol.*` – pure framing / checksum / decode (host-testable, no hardware).
- `rak9154/RAK9154Battery.*` – cache, state machine (provision -> poll), timeouts, stats, CLI text.
- `rak9154/RAK9154HalfSerial.*` – bit-banged half-duplex UART on one pin (GPIOTE falling-edge RX, DWT-timed TX).
- Poll every 30 s (clamped 15–60 s); cache is stale after 5 min; 1.5 s response timeout; re-provision after 3 timeouts.
- Blocking: only transmitting a request (~14 ms/poll). RX is interrupt-fed (~1 ms of ISR time per received byte).

| flag | default | meaning |
|---|---|---|
| `RAK9154_BATTERY` | off | enable feature |

| `RAK9154_DEBUG` | off | serial log lines |
| `RAK9154_POLL_INTERVAL_MS` | 30000 | |
| `RAK9154_STALE_MS` | 300000 | |
| `RAK9154_RESPONSE_TIMEOUT_MS` / `RAK9154_REPROVISION_AFTER` | 1500 / 3 | the custom env uses 4000 / 10 during bring-up |
| `RAK9154_RSP_BIG_ENDIAN` / `RAK9154_REPORT_BIG_ENDIAN` | 0 / 1 | **UNVERIFIED** 16-bit byte order |
| `RAK9154_TX_GAP_BITS` | 4 | idle bit times after every transmitted byte (RAK's reference class spaces bytes ~12 bit times; change live with `rak9154 gap <n>`, 0-16, not persisted) |
| `RAK9154_RX_LATENCY_CYCLES` | 320 | ISR entry latency used to centre sampling; tune with a scope |

## CLI

`rak9154` (same as `rak9154 status`), `rak9154 diag`, `rak9154 extra`, `rak9154 gap [n]`, `rak9154 poll`, `rak9154 info`, `rak9154 raw [offset]` (pages through the last received frame; replies are limited to ~150 characters, so use e.g. `raw 35` and `raw 70` for the rest). `status` shows validity, voltage,
age and the diagnostic counters (requests, ok, timeouts, bad checksum, invalid, framing, unknown channels, range rejects).

## Pin verification (REQUIRED before connecting anything)

The GPIO carrying Output 1 on a WisMesh repeater harness was **not** established from documentation. The default
(P0.15) is what RAK's library and a Meshtastic RAK variant use, nothing more. Before powering:
1. Trace the RAK9154 Output 1 wire to the WisBlock slot pin with a multimeter/continuity (unpowered).
2. Find that pin's nRF52840 GPIO in the RAK4631 schematic; confirm it is not used by the radio, I2C, GPS, or LEDs.
3. Check the probe's logic level is 3.3 V before it touches an nRF52 pin.
4. Set `-D RAK9154_ONEWIRE_PIN=<arduino pin>` accordingly. Note the GPS option uses some of the same header pins,
   which is why the custom target disables GPS.
5. First power-up: scope/logic analyser on the line if possible; confirm 9600 baud idle-high frames.

## Channels decoded

Per [RAK's RAK9154 payload decoder](https://docs.rakwireless.com/product-categories/accessories/rak9154/payload-decoder/)
(that page documents the LoRaWAN uplink of a RAK2560 hub, which shares the sensor IDs; the one-wire byte order is
separate and still unverified here):

| IPSO | field | size / scale |
|---|---|---|
| `0xBA` | battery voltage | 2 B unsigned, 0.01 V |
| `0xB9` | battery current | 2 B signed, 0.01 A (+/-1.5 A range) |
| `0xB8` | state of charge | 1 B, % |
| `0x67` | temperature | 2 B signed, 0.1 C (-30..105) |
| `0xF3` | battery errors **and** battery FW version | 2 B; faults are bits 6..11: 6 over-voltage, 7 charge over-current, 8 charge low-temp, 9 charge high-temp, 10 charge short-circuit, 11 charge over-current lock |

The two `0xF3` entries are told apart only by their channel byte, and RAK documents the channel only for the FW
version (example `0x1A`). The driver stores both raw with their channels; `rak9154 extra` shows them, labelling a
word with any bit outside 6..11 as a firmware version and 0 as "no faults". That labelling is a heuristic until it is
seen on a real probe. Not yet published over the mesh (Phase 2).

## Byte-order bench procedure

Voltage endianness is unverified. With a battery of known voltage: run `rak9154 raw` and `rak9154 info`, compare the
decoded value. A `range rejects` count rising means the byte order is wrong; flip `RAK9154_RSP_BIG_ENDIAN` /
`RAK9154_REPORT_BIG_ENDIAN` and re-test. Please contribute real captures to `test/test_rak9154/fixtures.h`.

## Tests

Host tests (53 protocol/driver tests + 15 simulated-hardware tests of the real transport source), ASan/UBSan:
see `.github/workflows/build-rak9154.yml` for exact commands. The existing fixtures are **synthetic**, built from
an independent encoder; they prove internal consistency, not agreement with a real probe.

## What has and has not been verified

Verified in the development sandbox: host tests; cross-compile of all new/changed sources for Cortex-M4 against the
real Adafruit nRF52 headers; with the flag off the board code disassembles identically to upstream and the new
sources compile to empty objects; the new env equals the stock env plus four flags.

**Not verified** (CI/bench needed): full PlatformIO build of both targets (registry unreachable in the sandbox),
booting, any communication with a real RAK9154, the pin, byte order, whether the probe needs provisioning, RX timing
margin under radio/USB interrupt load, and any temperature/status field meaning.

## First hardware observation (2026-10-22)

Real probe: model `RAK2560-io`, hw 0x44, sw 1.2.9, six sensors `BA B9 B8 67 F3 F3`; old-firmware framing (LEN one less
than the header's payload length). The wiring/pin and receive path work: the provision announcement is received,
checksummed and decoded, and answered. Get-data requests then went unanswered (0 ok frames, 17 timeouts) with the
original defaults. Under investigation; use `rak9154 diag` to see request/provision/receive counters.

Second observation (`diag`: req 259 = prov 259 = rxfr 259, 23896 rx bytes): the probe answered **every** request,
including get-data, with a fresh 91-byte provision announcement, i.e. it never accepted our provisioning reply and
stayed "unprovisioned" (source 0xFF). Our reply is byte-for-byte what RAK's reference master builds (echo of the
announcement with flag=RSP, swapped addresses, provId set, checksum recomputed), so suspicion moved to the physical
layer: we sent the 92-byte reply back-to-back (10 bit times/byte) while RAK's class spaces bytes by extra idle time.
Hence `RAK9154_TX_GAP_BITS` / `rak9154 gap`. The driver now also backs off (2 s, 4 s ... up to the poll interval)
instead of answering a stubborn probe twice a second.

## First successful hardware reading (2026-10-22)

With `rak9154 gap 4` the probe (RAK2560-io, sw 1.2.9) answered: `V:12.31V I:41mA SOC:99% T:21.0C ok:15 to:0 cs:0 inv:0`.
The default byte orders (responses little-endian) therefore look right: the values are plausible, but compare
them with a multimeter on the battery before trusting them. The probe also re-announces itself every ~8 s while
delivering data, so the driver answers repeated announcements at most once per 60 s while data is fresh
(`skip:` counter in `rak9154 diag`). Only gap 4 has been confirmed to work; 0 failed before the back-off fix and 2 was
not tested separately.
